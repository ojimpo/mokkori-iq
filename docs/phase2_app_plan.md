# Phase 2 スマホアプリ 開発プラン (2026-07-28 策定)

次セッション以降の実装ガイド。前提となる確定事項は CLAUDE.md「Phase 2」節と
`docs/ble_time_sync_design.md`、Strava の出し方は CLAUDE.md「Strava 投稿の規約」を参照。

## ゴール
泳ぐ → デバイスを叩いて BLE で吸い出し → アプリが解析 → **壁インターバル表で確認・修正** →
Strava へアップ、まで iPhone だけで完結させる（タブレット・Mac を運用から外す）。

## 確定済みの設計判断（再掲・要点のみ）
- iPhone / Swift ネイティブ（SwiftUI + CoreBluetooth）。
- デバイス = 記録＋コーザル壁カウンタ（振動用）のみ。**非コーザル解析はアプリ側で実行**。
- **生データ（6軸 int16 + アンカー）はアプリ内に永続保存**。編集（壁の追加/削除/マージ）は
  生データを書き換えず**オーバーレイとして別保存** → 検出器改良時に過去セッションを再処理できる。
- 確認画面 = 壁インターバル表。ハイライト: 中央値の ≳1.6倍=見逃し疑い / ≲0.6倍=偽壁疑い /
  壁 vs ペース推定の不一致（CROSS-CHECK）。リズムリカバリで補完した壁は明示。
- Strava は手動アクティビティ POST。表示時間=泳ぎのみ(moving)、開始時刻=泳ぎ始め、
  距離=最良推定（保守バイアス撤廃済み。「控えめ」等の断り書きは書かない）。

## リポジトリ配置
**mokkori-iq リポジトリ内の `app/` に置く**（別リポジトリにしない）。
理由: 解析の Python 実装が Swift 移植のリファレンスで、パリティテスト（下記）が
`data/swim/*.csv` と `analysis/regression_check.py` の期待値を直接参照するため。
グローバルルールの「新規アプリは ~/dev/{名前}/ + Docker」は Web アプリ向けであり iOS には適用しない。

## フェーズ分割（BLE を待たずにアプリの大半を作れる順序にしてある）

### Phase A: 解析エンジンの Swift 移植 + 確認画面（BLE 不要・最初にやる）
既存の CSV（`data/swim/` に2セッション分ある）をファイル取込して動かす。実機ファーム変更なし。
1. Xcode プロジェクト作成（`app/`、SwiftUI、iOS 17+、iPhone 専用）。
2. コアの移植（`turn_stand.py` → Swift）: EMA → verticality 自己キャリブレーション →
   エピソード分類 → デフラグ → リズムリカバリ。次に `swim_report.py` 相当
   （typical length time・レップ分割・min() クロスチェック・SPM は後回し可）。
3. **パリティテスト（最重要）**: XCTest で `regression_check.py` と同じ期待値を固定
   （6/21: turns=35/rests=13/bigs=2/recovered≈724s/500+675=1175m、
   7/28: turns=41/rests=1/bigs=3/recovered≈533s/625+425=1050m）。
   バンドルした 2 セッションの CSV に対して Python と同一の結果が出たら移植完了とみなす。
   ※float の EMA 累積は誤差が出るので Double で実装し、壁時刻は ±0.5s 許容で比較。
4. UI: セッション一覧 → レポート画面（距離/ペース/レップ内訳）→ **壁インターバル確認画面**
   （表 + ハイライト + 壁の追加/削除/マージ + 即時再計算）。
5. データモデル: セッション（生サンプル列 + メタ + 時刻アンカー）と編集オーバーレイを分離して永続化
   （SwiftData か生ファイル+JSON。生サンプルはバイナリのまま保存が容量的に有利: 9.6MB CSV → 2MB バイナリ）。
6. 取込は当面「ファイル」アプリ/AirDrop 経由の CSV インポート（flash_dump の CSV がそのまま入る）。

### Phase B: Strava アップロード（2026-07-28 実装済み。残りは API アプリ登録＝ユーザー作業）
1. OAuth: **アプリは Strava を直接叩かず、`strava-autopilot` を Strava ゲートウェイにして経由する**方針に決定
   （詳細と理由は CLAUDE.md「Strava 投稿の規約」の認証節）。Strava は 1 アカウント 1 アプリ、かつ
   **2026-06 以降は API 利用に Strava サブスクが必須**なので、無料サブアカウントでの新規登録は不可。
   トークンを持つのを NAS 側だけにすることで、既存の autopilot を壊さず `client_secret` もスマホに置かずに済む。
   実装: `StravaService`（`POST /api/gateway/activities` を `X-API-Key` で呼ぶだけ）。
2. 確認画面 →「アップ」で手動アクティビティ POST（規約どおり: moving time / 泳ぎ始め開始 /
   名前は時間帯デフォルト）。アップ済みフラグと activity id をセッションに保存。
   投稿内容の組み立ては `MokkoriCore/StravaSummary`（Swift 側が規約の実装）。
3. 時刻アンカーが無いセッション用に、手動アンカー入力 UI（「泳ぎ始め」または「記録終了」1 点から逆算。
   7/28 で実証済みの方法）を暫定で付ける。BLE 時刻同期が入るまでのつなぎ。

### Phase C: ファーム時刻アンカー（USB 完結・Todoist「ログに現在時刻」ステップ1）
アンカー記録 + `TIMES` コマンド + flash_dump/dataio の unixtime 列。BLE 抜きで検証できる安全な一歩。
アプリ側 Phase A/B と並行可能（Mac 作業）。

### Phase D: BLE（ファーム + アプリ）
1. ファーム: Bluefruit 導入 + タップ起動 + GATT 設計（時刻書込 / INFO / フルダンプ転送）。
   要実機検証: BLE と記録 52Hz の共存、タップ誤作動（3タップ境界マーカー・泳ぎと取り違えない）。
2. アプリ: CoreBluetooth で 時刻同期 → ダンプ受信（2MB ≒ 実効 20〜40kB/s で 1〜2分）→
   Phase A のパイプラインへ。CSV インポートは開発・保険用に残す。
3. 通し確認ができたらタブレット運用を引退。

### Phase E: 仕上げ（順不同）
- **レポート画面のペースグラフ**（設計済み: `docs/pace_chart_design.md`）。
  縦軸=距離で上から下へ、1本25m=1バーの左端揃え。右端の輪郭でビルドアップ／垂れを読み、
  平均線・傾向線を重ね、異常値だけ色と直接ラベルで浮かせる。
  将来はバーのタップから壁インターバル確認画面の該当行へ飛ばし、「変な1本を見つける→直す」を一続きにする。
- SPM（ストローク率）の移植、履歴・集計画面、検出器更新時の一括再処理ボタン、
  修正ログの書き出し（＝ラベル付きGT。Mac の Python 側チューニングへ還流）。

## ガーミン互換メトリクス（2026-07-28 検証。「ガーミンで見れる指標をできる限り」がユーザー要望）
25m×2セッションの実データで本ごとのストローク数カウントを検証済み（バンドパス 0.3–1.2Hz →
最良ジャイロ軸のゼロクロス実カウント。スペクトル推定 周波数×時間 と中央値±1以内で一致）。
結果: **15 サイクル/25m（IQR 14–15）**、ペース30秒/25m・ストローク率30cyc/minと整合。
ガーミンの腕時計は「時計側の腕のストローク数」を数える仕様なので、**ロールサイクル数（左右1往復=1）が
そのままガーミンのストローク数と同じ土俵**になる。

| 指標 (Garmin プールスイム) | 状態 |
|---|---|
| 距離・本数 | ✅ 実装済み (壁検出) |
| 泳ぎ時間 / 経過時間 / 休憩時間 | ✅ 実装済み |
| 平均ペース /100m | ✅ 実装済み |
| ベストペース（最速の本） | ✅ 実装済み (2026-07-28 swim_report + Swift) |
| **ストローク数（本ごと / 合計 / 平均）** | ✅ **実装済み** (2026-07-28 swim_report + Swift。下記注) |
| ストローク率 (strokes/min) | ✅ 実装済み (30 cyc/min ≒ 60 arm strokes/min) |
| SWOLF（平均 / ベスト） | ✅ 実装済み（この泳者 実測 平均44・ベスト38） |
| DPS（1ストローク距離） | ✅ 実装済み（実測 1.79m/cycle） |
| インターバル / セット構造・レスト時間 | ✅ 実装済み (rest / big-rest) |
| 泳法判定 | ⏸ 自由形のみの運用なので固定ラベル（将来課題） |
| カロリー | 🟡 概算可（MET×体重×時間。精度は期待しない） |
| 心拍・トレーニング効果 | ❌ センサ無し（光学HRは水中不利。やるなら将来ハード拡張） |

実装順: まず Python 側 `swim_report` に本ごとメトリクス（ストローク数/SWOLF/ベストペース/DPS）を追加して
リファレンスにする → Phase A の Swift 移植・レポート画面/確認画面の列に含める。
プロトタイプの注意: ウォームアップ区間・退水区間は prone ゲートを掛けないとゴミカウントになる
（6/21 の 0→最初の壁 150s 区間で125カウント等）。本の境界内でも prone 判定でマスクすること。

**実装済み (2026-07-28)**: swim_report.py（リファレンス）と MokkoriCore（Swift、パリティテストで同値ピン留め）の両方に実装。
移植容易性のため FFT/scipy を使わず「RBJ バンドパス biquad（因果・0.3–1.2Hz）→ prone ゲート付きヒステリシス
ゼロクロス」で実カウント。**committed 実装の中央値は 14/本（IQR 13-14）**（上記スクラッチ検証の 15 と ±1 差 =
スペクトル整合の範囲内。SPM 30cyc/min × 泳ぎ約29s/本 ≈ 14.5 なのでどちらも妥当）。両セッションとも全本計測可
（47/47・42/42）、SWOLF 平均44・ベスト38、DPS 1.79m。期待値は regression_check.py と ParityTests に固定済み。
