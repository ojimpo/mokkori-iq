# ペースグラフ設計 (2026-07-28 策定・同日実装済み)

> **実装済み。** データモデルは `app/MokkoriCore/Sources/MokkoriCore/PaceChart.swift`、
> 描画は `app/MokkoriIQ/Sources/Views/PaceChartView.swift`。
> 設計どおりに作れなかった／作ってみて分かったことは末尾の「実装で分かったこと」に追記してある。

レポート画面に「ラップごとのペース」を可視化するグラフを入れる。
実装対象は `app/MokkoriIQ`（SwiftUI + Swift Charts）。データ源は `SwimReport.laps`。

## 何を作るか

Strava のラップ別ペースグラフを**縦横反転**したもの。

- **縦軸 = 距離。上から下へ 0m → 1000m**（泳ぎ進む向きと同じ）
- **1ラップ（25m）= 1 バー。左端揃え**（Strava と同じく、バーの端が輪郭線になる）
- **1000m が 1 画面に収まる**（＝バーはかなり細くなる）
- **平均ペースを縦線で 1 本オーバーレイ**

**このグラフが答えるべき問い**（ユーザーの言葉。ここが形を決める）:

1. 1000m を通して **ビルドアップできているか、垂れていくか**
2. **異常値が一目で分かるか**

## 結論

**左端揃えの横バー + 横軸はデータ範囲に切る + 平均線を重ねる。**
異常値だけ色を変えて直接ラベルを付ける。

```
        1:42        平均 2:02              2:17
   0m  ┤▓▓▓▓▓▓▓▓▓▓▓▓▓┊
        ┤▓▓▓▓▓▓▓▓▓▓▓▓▓┊▓
        ┤▓▓▓▓▓▓▓▓▓▓▓▓┊         ← 右端の輪郭が「ペースの推移」そのもの
        ┤▓▓▓▓▓▓▓▓▓▓▓▓▓┊
  100m  ┼─────────────┼──────────  インターバル境界（レスト 12s）
        ┤▓▓▓▓▓▓▓▓▓▓▓▓▓▓┊
        ┤▓▓▓▓▓▓▓▓▓▓▓▓▓▓┊▓
        ┤▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓┊▓▓▓▓▓▓▓  ← 異常値（橙＋直接ラベル）
        ┤▓▓▓▓▓▓▓▓▓▓▓▓▓▓┊
 1000m  ┤▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓┊
                       ┊  ← 平均ペース（縦線）
        └ 左が速い          右が遅い →
```

- **バーは左端から右へ伸びる。長い = 遅い**（＝かかった時間が長い）。
- 右端の凸凹が**そのままペースの推移**になる。上から下へ目で追えば、
  だんだん短くなっていれば**ビルドアップ**、伸びていけば**垂れ**。
- 平均線は縦の基準線。異常値は色 + ラベルで浮かせる。

### 横軸は 0 起点にしない（実データで確認した）

棒グラフは本来 0 起点にすべきだが、**このデータでは 0 起点にすると目的を達成できない**。
7/28 セッション（42本）の実測で、プロット幅 300pt を仮定して比較した:

| 横軸の取り方 | IQR の幅 | 最速→最遅 | **10s/100m のドリフト** |
|---|---|---|---|
| 0 起点（0〜137s） | 20.9pt | 71.8pt | **20.9pt** |
| データ範囲に切る（97〜142s） | 67.6pt | 232.4pt | **67.6pt** |

ビルドアップ／垂れの信号は 1000m でせいぜい 10s/100m 程度。
0 起点だとそれが **21pt しか動かず、480pt の高さの中では傾きとして見えない**。
軸を切れば 68pt になり、輪郭線の傾きとしてはっきり出る。

**トレードオフの明示**: 軸を切ったバーは「長さが値に比例しない」ので、
本来は「2倍長い＝2倍遅い」と誤読させうる形（Strava も同じ妥協をしている）。
ここでは以下の理由で許容する。ただし**この判断は意識的に選んだものだと覚えておくこと**。

- 読み手は自分のデータを知っている本人ひとりで、軸ラベル（`1:42`〜`2:17`）を読む。
- 目的は絶対量の比較ではなく**推移と外れ値の発見**で、そこは軸を切らないと達成できない。
- 各ラップの絶対値は「ラップ」セクションの表とタップで正確に読める（グラフが唯一の読み口ではない）。

軸の下限・上限は**セッションのデータ範囲に少し余白**を足して決める（固定値にしない）。
ただし **1本あたり数秒の幅しかない極端に均一なセッション**では拡大しすぎるので、
最低でも `平均 ± 10s/100m` は入る幅を確保する（ノイズを山に見せない）。

### 却下した案: 平均を基準にした発散バー

当初こちらを推していたが、**「上から下へ流れとして読む」用途に向かない**。
バーが中心から左右に散るので輪郭が二股になり、ビルドアップ／垂れの傾きが追いにくい。
外れ値の発見だけなら優れているが、問い 1 が主目的なので不採用。

## レイアウト

### 縦軸（距離）

- スケールは **実距離**（ラップごとの矩形が `[d, d+25]` を占める）。カテゴリ軸にしない。
  連続軸にしておくと 100m の目盛りが物理的に正しい位置に来る。
- **上が 0m**。Swift Charts では `.chartYScale(domain: [total, 0])` で反転する。
- 目盛りラベルは **100m ごと**（25m プールなら 4ラップごと）。1000m で 10 本。

### 1 本あたりの高さ（＝1000m が 1 画面に収まる根拠）

| 項目 | 値 |
|---|---|
| 1 本（25m）の帯 | **12pt**（バー 10pt + 隙間 2pt） |
| 1000m = 40 本 | **480pt** |
| iPhone 17 Pro の論理高さ | 874pt |

480pt ならナビゲーションバーと軸ラベルを足しても 1 画面に収まる。
隙間 2pt は「隣接するバーの間は 2px の余白（枠線で区切らない）」という指針どおり。

- **1000m を超えるセッションは縦スクロール**（1本の高さは固定のまま）。
  セッションごとに縮めて全部を押し込むと、**バーの太さが変わってセッション間で比較できなくなる**。
  実測は 6/21 = 47本(1175m)、7/28 = 42本(1050m) なので、いずれも少しスクロールする。

## 重ねるもの

| 要素 | 表現 | 目的 |
|---|---|---|
| 平均ペース | 縦の `RuleMark`（マゼンタ・実線） | 基準 |
| 傾向の要約 | グラフ下に一行 `後半にかけて +4.2s/100m（垂れ）` | 数字でも言い切る |
| インターバル境界（レスト） | 距離軸上の水平ヘアライン（緑）+ 右端にレスト時間 `45s` | セット構造 |
| セット境界（大休憩） | 同じ緑で線を太く + `10:32 レスト` | セットの切れ目 |
| 異常値 | 色を変える + **そのラップだけ**直接ラベル | 問い2に直接答える |
| 最速の1ラップ | `ベスト 1:42` の直接ラベル | ハイライト |

- **全バーに数値を振らない**（読めなくなる）。ラベルは異常値とベストだけ。
- グリッド・軸は細い実線のヘアライン。**破線にしない**。

### 異常値の判定

ラップ確認画面のハイライト規則と揃える（別の基準を持ち込まない）。

- そのセットの**中央値の 1.25 倍より遅い**ラップ、または **0.75 倍より速い**ラップを異常値とする。
- 併せて、確認画面で `missedSuspect` / `falseSuspect` が付いたラップは同じ色にする
  （＝「ターンを見逃した／余計なターンを拾った」疑いはペースの異常として必ず現れる）。
- 判定はセット単位。ウォームアップとメインで基準が変わるため、セッション全体で見ない。

## 配色（検証済み）

一系列 + 強調（emphasis）の構成。**値の大小で色を変えない**（長さで既に表現されているため、
色まで使うと二重符号化になる）。異常値だけを強調色にする。

下の値はバリデータで **ライト・ダーク両モードとも全項目 PASS**（明度帯・彩度・
色覚多様性の分離 ΔE・通常視 ΔE・背景コントラスト）。

| 役割 | ライト | ダーク |
|---|---|---|
| 通常のバー | `#2a78d6` | `#3987e5` |
| 異常値のバー | `#eb6834` | `#d95926` |
| 平均線 | `#c0479f` | `#cf62ad` |
| レスト線 | `#2e9e6b` | `#35a273` |
| 軸・ラベル | `#898781`（両モード共通の muted） | 同左 |
| グラフ背景 | `#fcfcfb` | `#1a1a19` |

- ダークは自動反転ではなく**この値を明示的に指定する**。
- **色だけに意味を載せない**: 異常値には必ず直接ラベルを添える（色覚特性に依らず読める）。
- **状態色（good/warning/critical）は使わない**。「平均より遅い」は異常ではないので、
  赤で「悪い」と断じない。橙は「見てほしい」の強調であって評価ではない。

## 操作

- **バーをタップ → そのラップの詳細**（ラップタイム / ストローク数 / SWOLF / 通し何ラップ目か）。
  タップ判定はバー 10pt より広く取る（帯 12pt 全体 + 前後、最低 24pt 相当）。
- **詳細はバーに貼り付くツールチップで出す（2026-07-31、実機フィードバックで変更）**。
  当初はグラフの下に一行で出していたが、実機だと **①選択されたことに気づかない
  ②数字が凡例の下にあって目が行かない**。選択の合図は2つ:
  グラフ幅いっぱいの帯（どの行か）と、バー先端に付くツールチップ（何の値か）。
  - ツールチップは既定でバー先端の右。**遅いラップはバーが右端まで届く**ので、
    はみ出す場合は先端の左へ折り返す。上下もプロット内に押し込む。
  - **実装は Chart の中の `.annotation` ではなく `.chartOverlay`**。Charts の annotation は
    アクセシビリティツリーに出ないので、VoiceOver で読めず UI テストからも掴めない。
    overlay なら普通の SwiftUI なので両方効く（位置決めは `ChartProxy.position(forX:/forY:)` で自前）。
- 将来: タップでラップ確認画面の該当行へ飛ばす。
  **「変な1ラップを見つける → その場で直す」が一続きになる**のが狙い。

## 実装メモ

### データの取り出し

`SwimReport.laps` は泳ぎ順に並んでいるので、通し番号 `i` から
累積距離 `i * poolLength` が出る。ペースは `lap.duration / poolLength * 100`。

```swift
// 平均は「レポートの平均ペース」を使う（総泳ぎ時間 / 総距離）。
// ラップごとの平均を取り直すと、レポート上部の数字と食い違って混乱する。
let avg = report.pace100
```

### 注意すべき食い違い（要ハンドリング）

`laps.count * poolLength` は **`report.distance` と一致しないことがある**。
距離は `min(壁カウント, ペース推定)` を採るのに対し、`laps` は壁ベースで作られるため。
現状の2セッションでは min() が一度も発火しないので一致しているが、
**CROSS-CHECK が出たセッションではラップ数がずれる**。

→ グラフは `laps` をそのまま描き、距離軸の最大値も `laps.count * poolLength` にする。
レポート上部の距離と食い違う場合は、グラフの下に注記を出す（黙って辻褄を合わせない）。

### Swift Charts の使い方

- 各ラップは `RectangleMark(xStart:xEnd:yStart:yEnd:)`。`BarMark` を連続軸で使うと
  自動ビン分割がかかって 25m の帯にならない。
  `xStart` = 軸の下限、`xEnd` = そのラップのペース。
- 縦軸反転は `.chartYScale(domain: [totalMeters, 0])`。
- 平均線は `RuleMark(x: .value("平均", avg))`。
- バーの角丸は 4pt を**右端（データ側）だけ**に付ける。左端は軸に接するので角丸にしない。
- 高さは `.frame(height: Double(laps.count) * 12)` を `ScrollView` に入れる。
  **軸ラベルの帯を含めた高さ**にする（プロットだけの高さにすると軸が切れて内側スクロールが出る）。

## 実装で分かったこと (2026-07-28)

### 異常値の強調は、実データでは一度も発火しない

**この泳者のペースが揃いすぎている。** セット中央値に対する比は
6/21 が 0.87〜1.17、7/28 が 0.84〜1.12 で、判定値 1.25 / 0.75 に**どちらもかすりもしない**。
つまり橙のバーと直接ラベルは、現状の2セッションでは1ラップも出ない。

閾値は**緩めずに据え置いた**。理由は、この強調は「速い遅い」を評価するものではなく
**検出がずれた／本当に泳ぎが崩れた**ときに目を留めさせる非常口だから。
1.15 倍まで下げれば 6/21 で1ラップ光るが、それは「たまたま少し遅い1ラップ」であって
見てほしいものではない（ラベルが増えるぶん、本当の異常が埋もれる）。
実データで通らない経路になるので、**色が付く経路は合成データのテストで担保**してある
（`PaceChartTests.testOutlierEmphasis`）。

### 傾向線は引かないことにした（ユーザー判断）

設計では回帰直線を重ねる予定だったが、実装して見たら**平均線・レスト線と合わせて
3種類の線が交差して読みづらかった**。そもそもバーの右端の輪郭で傾向は読めるので、
**線は引かず、グラフ下の一行（`後半にかけて +13.2s/100m（垂れ）`）で言葉にする**。
回帰の計算自体は `PaceChart` に残っていて、その一行の数字がそれ。

- 回帰直線は**グラフの上端(0m)〜下端(総距離)まで**の値で評価する（ラップの中点の範囲ではなく）。
  テストの期待値もこの前提（中点間 +18s → 端まで引くと +20s）。
- 実測の傾向は 6/21 が **+5.9s/100m**、7/28 が **+13.2s/100m**。どちらも「垂れ」。
  7/28 はセット境界（10分のベンチレスト）でペースが一度戻るが、
  各セットの中でも垂れているので、セッション全体の回帰で言い切って問題なかった。
- 軸幅は 6/21 が 1:43〜2:22、7/28 が 1:41〜2:18。**輪郭の傾きは実際に目で読める**
  （設計時の計算どおり。0 起点にしていたら読めなかった）。

### Swift Charts の実際

- **角丸を右端だけに付ける方法が無い**（`RectangleMark.cornerRadius` は4隅すべて）。
  → 同色の四角を左端に 4pt ぶん重ねて左の角丸を潰している。4pt をデータ単位に直すため
  `GeometryReader` でプロット幅を取る。左端が直線に揃うことがこのグラフの読み方の要なので、
  ここは妥協しなかった。
- **レストのラベルは `position: .trailing` だとカード右端で切れる**（`10:32 レスト` が `1C` になった）。
  → プロットの内側（`position: .top, alignment: .trailing` + `overflowResolution`）に置く。
- `RectangleMark` を `BarMark` の代わりに使うのは設計どおりで正しかった（連続軸での自動ビン分割を回避）。
- グラフは `List` の1行として置いた。設計時は `ScrollView` を想定していたが、
  ページ全体のスクロールに乗るほうが入れ子スクロールにならない。
